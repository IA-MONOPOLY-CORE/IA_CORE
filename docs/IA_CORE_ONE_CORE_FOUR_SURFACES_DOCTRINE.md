# IA_CORE One Core, Four Surfaces Doctrine

## Status and authority

This is the single canonical strategic statement for the future product
relationship between IA_CORE's shared intelligence and its environment-specific
expressions. It is additive to the future platform documents and does not
duplicate their individual reservations.

`ONE_CORE_FOUR_SURFACES_DOCTRINE_DOCUMENTED`

> IA_CORE es un único sistema evolutivo con un solo núcleo canónico. Desde ese
> núcleo se expresan cuatro superficies de producto adaptadas a entornos
> diferentes. No son cuatro productos independientes, cuatro codebases
> autónomas ni cuatro desarrollos desde cero.

## The four surfaces

1. **`IA_CORE PLATFORM`** - portable platform hosted on existing systems,
   including Windows, Linux, servers, web, or cloud when current contracts and
   future authorization support them.
2. **`IA_CORE OS DESKTOP/SERVER`** - future native expression oriented toward
   control, performance, security, and dedicated resource management.
3. **`IA_CORE MOBILE`** - future Android and iOS application or companion.
4. **`IA_CORE MOBILE OS / MOBILE ENVIRONMENT`** - future native mobile
   expression built on compatible open foundations.

These are four product surfaces of one system, not four independent product
forks. The names describe strategic direction, not current implementation
status.

```text
                         IA_CORE CANONICAL CORE
                                  |
            +---------------------+---------------------+
            |                     |                     |
     PLATFORM HOSTED      OS DESKTOP/SERVER       MOBILE APP
                                                          |
```

The diagram is conceptual. It communicates one authority and four expressions;
it does not impose a technical repository topology. The four surfaces may be
represented as four direct branches of the same canonical core in future
architecture work.

## Shared canonical core

The core is the common authority for the following contract-governed concerns:

- identity;
- knowledge;
- GOKV, DOOL, and OCI;
- memory;
- agents;
- permissions;
- contracts;
- evidence;
- observability;
- security;
- lifecycle;
- integration;
- cumulative learning.

Each surface may add UI, adapters, drivers, packaging, runtime, and
environment-specific capabilities without forking the central truth. A surface
adapter may translate environment details, but it cannot invent authority,
permissions, payload state, evidence, or lifecycle transitions.

## Doctrine principles

- `ONE_CORE_FOUR_SURFACES` - one canonical intelligence and control authority.
- `NO_INDEPENDENT_PRODUCT_FORKS` - no separate truth or isolated product
  lineage for a surface.
- `SHARED_INTELLIGENCE_ENVIRONMENT_SPECIFIC_EXECUTION` - common intelligence,
  contracts, evidence, and learning with environment-specific expression.
- `PRESERVE_FUTURE_ARCHITECTURAL_OPTIONALITY` - keep viable future routes open
  without claiming they are built.
- `INTEGRATE_WHAT_WORKS_REPLACE_WHAT_FAILS_CREATE_WHAT_IS_MISSING` - reuse
  proven foundations and create only the missing contract-bound pieces.
- `EARNED_IRREPLACEABILITY` - retain users through utility, continuity,
  results, trust, and accumulated learning, never through lock-in, opacity, or
  data seizure.
- `HUMAN_AMPLIFICATION_WITH_SELECTIVE_SUBSTITUTION` - amplify human direction
  and automate only bounded work whose authority and recovery are explicit.

`EARNED_IRREPLACEABILITY` is a trust and utility principle, not a retention
mechanism based on captivity. `HUMAN_AMPLIFICATION_WITH_SELECTIVE_SUBSTITUTION`
does not remove human authority from sensitive or irreducible decisions.

## Future OS and open foundations

The future OS expression may optimize CPU, GPU, memory, network, storage, and
peripheral allocation for IA_CORE contracts inside a controlled environment.
It must never claim that literally all resources can be assigned to agents:
kernel, drivers, security, essential services, and system stability remain
necessary.

Linux, AOSP, and other open foundations may be used where they solve a proven
problem. IA_CORE identity must come from architecture, operation, contracts,
security, and experience, not from a cosmetic rename of an existing system.

## Maturation order

```text
IA_CORE Platform funcional
-> prueba controlada
-> uso real
-> múltiples negocios y clientes
-> evidencia operacional
-> aprendizaje acumulado
-> escala demostrada
-> contratos base para superficies nativas
-> planificación específica cuando Dirección lo autorice
```

This is a relationship of maturity, not a calendar and not an implementation
promise. No dates are invented. No kernel, drivers, AOSP, mobile packaging,
mobile OS, or native terminal work is opened by this doctrine.

## Explicit non-capability boundary

The four surfaces are future architectural expressions except where an
existing current contract explicitly says otherwise. This document does not create an installable OS,
mobile application, native terminal, cloud service, provider connection,
endpoint, integration, runtime, execution path, workforce, permission, or
product payload.

No future surface may bypass the canonical core's contracts, security, evidence,
lifecycle, privacy, or human authority. A future implementation requires its
own approved scope, contracts, permissions, isolation tests, recovery model,
evidence, and human review for sensitive actions.

## Reuse rule for future documents

Future strategic documents should link this doctrine instead of restating the
four surfaces or creating parallel definitions. Their responsibility is to
specify their own domain reservation, dependencies, unknowns, and revisit
trigger while preserving `ONE_CORE_FOUR_SURFACES`.
