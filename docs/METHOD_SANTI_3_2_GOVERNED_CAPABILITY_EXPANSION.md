# METHOD SANTI 3.2
## Governed Capability Expansion

## Status and authority

- `METHOD_SANTI_3_0`: preserved as the active adaptive direction layer.
- Applied Method inventory 2.1: preserved as the operational rule inventory.
- Standalone Method Santi 3.1: not present in the current repository.
- `METHOD_SANTI_3_2`: additive, active and evolving for governed capability expansion.
- Current source, contracts, tests and published checkpoints win over historical prose.
- This document does not open runtime, execution, providers, integrations, deployment or product authority.

Method Santi 3.2 refines an existing map. It does not describe later missions as
initial discovery. A mission may increase map resolution, close a gap, connect
known surfaces or prepare a frontier without pretending that the repository was
previously unknown.

## 3.2 rules

### Known Map Refinement

The repository map already exists. Later work may review, refine, increase
resolution, discover connections, close gaps and complete bounded capabilities.
It must preserve provenance and must not relabel refinement as initial discovery.

### Governed Surface Throughput

Mission scale is the largest surface that can be closed correctly while keeping
time, resource use, risk and rework governed. Throughput means useful governed
surface divided by those costs. Prompt count and raw work volume are not goals.

### Block, station and commit

A block is a coherent section that ends only when its pieces work together. A
station is a finished, validated and recoverable architectural piece. An action
is work inside a station. Each station produces exactly one non-empty commit.
Independent pieces are not merged for convenience and indivisible pieces are
not split to inflate commit count.

### Ambiguity-proportional prompting

Prompt density follows unresolved ambiguity and risk, not physical file volume.
One prompt may govern one coherent block containing all preauthorized stations.

### Repository field recommendation loop

Codex inspects the real repository, recommends a bounded route, materializes
only authorized work, validates it and recalculates the frontier. The architect
uses that evidence to shape the envelope. Direction retains purpose, priority,
values, risk and irreducible human authority.

### Cumulative frontier preparation

Every station records `FRONTIER_AT_MISSION_START` and
`FRONTIER_AT_TIME_OF_ARRIVAL`, then identifies evidence, dependencies and the
next safe station. A classification may change only because the path produced
new admissible evidence.

### Progressive frontier compression

Prepare a frontier by naming its cause, missing evidence, preparatory stations,
remaining options and reversibility. Do not preserve a hard classification by
documentary inertia or dissolve one by optimism.

### Relevance-complete, scope-bounded inheritance

OCI selects all knowledge relevant to the mission within valid scope and
resource boundaries. It excludes irrelevant, stale, duplicate, unresolved,
private, out-of-scope or resource-incompatible knowledge. If resources are
limited, selection records the priority rule and the excluded remainder; it
never omits relevant knowledge silently. `CURRENT_CONTRACT_WINS` remains the
authority rule.

### Mandatory learning lifecycle

New operational learning enters a governed lifecycle. The system must preserve
learning, provenance, scope, evidence, contradictions, limitations and
replacement history. Promotion is never automatic. Promotion occurs only when
criteria pass and explicit governance permits it. Failed promotion preserves
the assessed result and reason.

### Domain capability extraction

Domain behavior is decomposed into attributes and behavior. Only demonstrably
reusable behavior becomes a global contract; domain-specific behavior remains
in the domain and uses an explicit adapter when needed. Renaming is not
globalization, duplication is not extraction, and movement requires equivalence.

### Capability map model

The map analogy explains different resolutions, unlocked capabilities,
checkpoints, validated shortcuts, combinable tools and shrinking frontiers. A
shortcut reuses validated contracts, evidence and tools; it never skips gates.
The analogy is explanatory and is not a runtime contract.

### Scale neutrality

New contracts must avoid blocking small, large, massive, multi-business or
concurrent evolution. They must not claim that any of those scales are already
operationally supported without evidence.

### Human and AI team authority

Direction defines purpose, priorities, values, risk and irreducible decisions.
The architect interprets, connects and compiles. Codex inspects, recommends,
materializes, validates and recalculates. IA_CORE preserves contracts,
capabilities, evidence and learning. More autonomy reduces repetitive
technical intervention; it does not remove human authority.

### Autonomy by maturity

Future broad autonomy is a direction, not a current capability. A phase can be
run with little or no intervention only after its decisions are expressed by
contracts, policies, evidence, tests, recovery and institutional knowledge.
Correct closure, not wall-clock duration, defines success.

## Execution contract

The standard path is:

```text
ONE PROMPT
-> ONE COHERENT BLOCK
-> N ARCHITECTURAL STATIONS
-> ONE COMMIT PER STATION
-> ONE INTEGRATED CHECKPOINT
```

Each station must state its input, postcondition, files, tests, frontier,
rollback boundary, affected evidence and next safe route. A true-hard or
external frontier pauses only its dependent branch; independent authorized
branches may continue. B-7 and phase closure always require their own evidence
and human acceptance.
